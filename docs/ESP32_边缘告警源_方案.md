# ESP32 当"边缘告警源"接进 SecTriage · 实施方案

> 一句话：**不是加一个传感器，是把降噪的第一层从服务端挪到设备上**，
> 顺手拿到三件只有真硬件才有的东西——不可信时钟、会重复投递、会重启。

---

## 0. 先说清：这件事为什么对你"有真实提升"

你现在面试被质疑的点不会是"你没做过硬件"，而是**"你的数据是合成的吧"**。所以判断标准只有一个：
**这条链路能不能产出别人造不出来的证据。**

| 加上设备后你能说 | 之前不能说 | 为什么造不出来 |
|---|---|---|
| 设备没有可靠时钟，所以我用 `boot_id + seq` 排序，服务端按接收时间落 `ts` | 只能说"我按时间窗聚合" | 造假的人不会想到"设备不知道现在几点" |
| 断网 30 秒，缓冲 200 条，恢复后补传，服务端幂等去重，**0 丢失** | 只能说"我做了容错" | 需要真的拔网、真的看数据 |
| 设备重启本身就是一条可用性告警（区分 panic / 看门狗 / **供电不足**） | 没有这一层 | `ESP_RST_BROWNOUT` 这种词，没摸过板子的人写不出来 |
| 每 5 秒一个窗口 = 一天 17280 个窗口；按窗口全量上报就是 17280 条/天，事件化后只剩异常那几条 | 只有服务端降噪比 | 需要边缘真的在跑，而且要量过基线 || 心跳单独一条通道，**不进研判管线**（否则每 5 分钟一条噪音） | 没有这个边界 | 这是设计过才有的判断 |

**加分的本质是"失败模式的真实度"**，不是"多接了一个模块"。

## 1. 明确不做什么（防止跑偏）

| 不做 | 原因 |
|---|---|
| 摄像头 + 图像识别 | 会变成第二个项目，把你的精力从 Agent 主线拽走 |
| 温湿度 / 门磁"上报即告警" | 烂大街，且和"告警研判"没有结构关系 |
| WiFi 去认证攻击、抓包破解 | 合规风险，且与 Agent 岗无关。**只扫自己的环境** |
| 把设备事件写进 `alerts.jsonl` | 会让"3000 条 → 40 个事件 / 98.7%"这些数字不可复现，别人一跑就对不上 |
| 上 K8s / MQTT broker / 时序数据库 | 单设备单机，上一个中间件就多一个面试要圆的坑 |

## 2. 链路

```
ESP32（每 5 秒采样，本地判定）        PC 上已有的服务
┌──────────────────────────┐        ┌──────────────────────────────────────┐
│ 探测请求计数（混杂模式）  │        │ POST /ingest                         │
│ 同名 SSID 检测（扫描）    │──事件──▶ 校验 → 幂等去重(boot_id+seq) → 落盘   │
│ 窗口越界判定 + 去抖       │  HTTP  │              │                       │
│ 环形缓冲 200 条 + 重发    │        │              ▼                       │
│ 心跳（不产告警）          │        │ 转成标准告警字段（asset/rule/tech/sev）│
└──────────────────────────┘        │              │                       │
                                    │              ▼                       │
                                    │ 聚合 → 富化 → 研判 → 决策（一行没改） │
                                    └──────────────────────────────────────┘
```

**关键取舍：设备只判断"这一批采样里本地窗口是否异常"，不做"这是不是攻击"。**
安全判断留在服务端——因为设备上没有上下文（不知道资产重要性、不知道历史基线、不能查 SOP）。

## 3. 事件契约（固件按这个发，服务端按这个收）

```json
POST /ingest
{
  "device": {"id": "esp32-lab-01", "boot_id": "b7c1", "fw": "1.0.0"},
  "events": [
    {"seq": 12, "dev_ms": 83000, "kind": "probe_surge", "value": 47,
     "detail": {"ip": "192.168.1.42", "window_s": 5, "baseline": 12}}
  ]
}
```

| 字段 | 为什么这么设计 |
|---|---|
| `boot_id` | 每次上电/重启随机生成。**没有它，重启后 seq 归零会被当成重复丢掉** |
| `seq` | 设备内自增，RTC 内存里保留（软件重启不清零）。幂等键 = `boot_id + seq` |
| `dev_ms` | 上电后的毫秒数，**只用来算设备端窗口长度，不参与排序** |
| `value` | 触发时的原始数值（47 次探测请求），留证据用 |
| `detail.ip` | 设备自己的局域网 IP，落进 `src_ip` 供富化用 |

**服务端的 `ts` 一律用接收时间**，因为设备时间不可信。这条要在文档和面试里都讲。

### 事件类型

| kind | 规则名 | ATT&CK | 严重级 | 是否产告警 |
|---|---|---|---|---|
| `probe_surge` | 无线探测请求突增 | T1595 | medium | ✅ |
| `ap_rogue` | 疑似钓鱼热点(同名SSID) | T1557 | high | ✅ |
| `device_reboot` | 边缘设备重启 | （空） | low | ✅ |
| `device_offline` | 边缘设备心跳丢失 | （空） | medium | ✅ |
| `heartbeat` | 心跳 | （空） | info | ❌ **不产告警** |

**两个刻意的设计**：
1. **可用性事件不套 ATT&CK**。硬对齐会让 `technique` 变成噪音，按 technique 统计时被污染。
2. **心跳不进研判管线**。否则一台设备每 5 分钟制造一条噪音，等于把边缘降噪的成果还回去。

## 4. 边缘判定算法（固件里就这三段）

```
每 5 秒一个窗口：
  cnt = 本窗口抓到的 Probe Request 帧数
  阈值 th = max(baseline × 3, 25)      # 25 是地板，防止低基线时抖动误报

  若 cnt > th:  over++ else: over=0; baseline = (baseline×9 + cnt)/10   # 指数平均

  上报条件：over ≥ 3（连续 3 个窗口）  且  距上次上报 > 5 分钟（冷却）
```

三个参数都不是拍脑袋的，面试要能说清：

| 参数 | 值 | 理由 |
|---|---|---|
| 窗口 | 5 秒 | 太短噪声大，太长事件边界糊掉 |
| 连续窗口数 | 3 | 单窗口尖峰会被 WiFi 扫描本身干扰，连续 3 个才算持续 |
| 冷却 | 5 分钟 | 一次异常持续时不要刷屏；这也是"告警抑制"的雏形 |
| 地板阈值 | 25 | 基线可能被算得很低，纯倍数判定会疯狂误报 |

## 5. 四个必须真做的实验（做完才有数字）

> 这一节是整件事的核心。**不做实验，ESP32 就只是玩具。**

### 实验 1：降噪比（证明"降噪在边缘发生"）

**先说清口径（我之前写错过一次，这里按实测重算）**：

- 固件是**每 5 秒汇总一个窗口**，每窗口 1 个计数样本 → **一天 17280 个窗口**
- 若"每个窗口都上报"，就是 **17280 条/天**
- 实际只在**连续 3 个窗口越界**时才报 → 取决于环境，空闲时 0 条

**已实测的基线（2026-10-26，COM7，三次共 38 个窗口）**：

| 场景 | min | 中位 | 均值 | max | 越界 |
|---|---|---|---|---|---|
| 空闲（家/办公室静态） | 3 | 12 | 12.6 | 20 | 0 |
| 单台电脑扫描（`netsh wlan show networks` 循环） | 3 | 14 | 12.8 | **28** | 0 |

**字节量估算**（一条上报 JSON ≈ 250 字节）：
```
全量：17280 条/天 × 250B ≈ 4.2 MB/天
事件化：假设 10 次异常/天 × 250B ≈ 2.5 KB/天
→ 约 1700 : 1
```
> 这个 1700:1 是**算出来的，不是测出来的**——`10 次/天` 是我拍的假设，你要在真机跑一天才能替掉。面试时把假设说出来，比给一个精确但来路不明的数字强。

**还缺的一步：真机触发一次 surge**（我这边单台电脑最高只到 28，够不到阈值 40）：

```
# 1) 起后端（新窗口，别关）
python main.py --host 0.0.0.0 --port 8200

# 2) 开测（60 秒）
python scripts/serial_lab.py --measure 60

# 3) 测试期间：拿手机站在板子旁边，反复「开/关 WiFi」或进出 WiFi 设置页点扫描
#    要连续 15 秒以上（= 3 个窗口）才会上报，这是刻意的去抖
```
成功标志：串口出现 `[surge] 探测请求 N > 阈值 40`，且 `serial_lab.py` 统计里 `触发 surge: 1 次`；后端 `/clusters?with_device=true` 出现 `无线探测请求突增`。

### 实验 2：断网补传（证明"0 丢失"）

- **操作**：拔掉/关掉路由（或把 PC 防火墙临时拦 8200），让设备攒 30 秒 → 恢复
- **要记**：`/device/events` 的条数在断网前后是否连续；设备串口打印的 `丢弃 0`
- **结论话术**：*"断网 30 秒，设备缓冲了 N 条，恢复后一次补传完成，服务端按 boot_id+seq 去重，最终 0 丢失、0 重复入库。"*

### 实验 3：重复投递幂等（证明"能安全重放"）

- **操作**：`python scripts/device_sim.py --scenario dup`（把整批原样重发）
- **要记**：返回 `accepted=0, duplicated=N`
- **已验证**：见下方"已验证结果"

### 实验 4：重启与掉线可见（证明"可用性也是告警"）

- **操作**：按板子 RST / 拔电；再让设备断网超过 120 秒
- **要记**：`device_reboot` 的 `detail.reason`（power_on / task_wdt / brownout）；`device_offline` 只出现一次（同一次沉默不重复报）
- **加分点**：如果你测出 `brownout`，说明供电不足——**这是硬件项目最真实的坑**，能讲。

## 5.5 调参记录：一个真实的踩坑（值得单独写）

**最初的参数是拍的**：阈值地板 `25`，理由"避免低基线时误报"。

**实测之后发现它是错的**：

| 观测 | 数据 | 结论 |
|---|---|---|
| 空闲基线 | 38 个窗口，中位 12，max 20 | 地板 25 只有 2.5× 中位，余量太小 |
| 单台电脑正常扫描 | 单窗口最高 **28** | **正常行为就能顶破 25** |

也就是说，地板 25 的意义是"**任何人扫一下 WiFi 都可能触发告警**"。虽然还要连续 3 个窗口，但那只是把误报从"立刻"推迟到"15 秒后"。

**改法**：地板 → `40`（约 3× 中位），保留"连续 3 窗口 + 5 分钟冷却"。

**这条为什么值得写进文档**：阈值不是拍脑袋定的，也不是抄来的，是**量了 38 个窗口之后定的**。
面试被问"你这个阈值怎么来的"，答"我量了基线，中位 12、最大 20，单台设备扫描能到 28，所以地板取 40"——
这句话的分量，比"调了几次试出来的"重得多。

**同时暴露一个更深的问题**：单台设备扫不出阈值，说明这个阈值其实在**识别"多人/多设备持续在场"**，
而不是"有人在扫描"。如果你想要的是后者，就得换信号（比如看 probe request 的目的 SSID 是否含不存在的前缀），
不是调阈值。**这个认知边界比参数本身重要。**

## 5.6 v1.1 零外设扩展：只用板子本身再加三个信号

手上没有任何模块（没传感器、没屏幕、没杜邦线）时，这块板子自己就带这些：

| 板载资源 | 当什么用 | 需不需要外设 |

| 芯片温度 / RSSI / 重连次数 | 设备健康度 | 不用 |

## 5.7 v1.1 真机踩的四个坑（这几个只有上板子才会遇到）

### 坑 1：BLE 和 WiFi 混杂模式抢射频 → BLE 扫不到任何设备

现象：串口完全没有 `[ble]` 输出，一度以为 BLE 初始化失败。

原因：WiFi 混杂模式把射频钉在"收 802.11 管理帧"的状态，BLE 扫描拿不到结果。

修法：**扫 BLE 前先 `esp_wifi_set_promiscuous(false)`，扫完立刻开回来**。
代价：这 2 秒内的 probe request 会漏数——**这个代价必须写进文档，不能说"没有影响"**。

### 坑 2：开 BLE 后 flash 直接 134%，编译报 "text section exceeds available space"

```
Sketch uses 1763179 bytes (134%) of program storage space. Maximum is 1310720 bytes.
```
修法：换分区方案 `PartitionScheme=huge_app`（3MB APP，无 OTA）→ 变成 56%。
**代价要说清**：huge_app 没有 OTA 分区，意味着不能空中升级，只能插线烧。

### 坑 3：心跳 300 秒、掉线阈值 120 秒 → 设备"永久假离线"

现象：板子明明活着、心跳正常，后端却一直报 `device_offline`。

原因：掉线阈值比心跳间隔还短，设备在两次心跳之间**必然**被判死。

规则：**掉线阈值 ≥ 3 × 心跳间隔**（允许丢 2–3 次心跳再判死）。
已改成心跳 60 秒、阈值 180 秒。

> 这个坑只有接上真设备才会暴露——纯模拟器永远测不出来，因为模拟器想发就发。

### 坑 4：基线只在"不越界"时更新 → 环境变了就永久误报

现象：BLE 侧默认基线 6，而实际环境本来就有 19 台设备 → 立刻越界，
而且因为"越界时基线不更新"，会永远越界，每 5 分钟报一次。

修法两条：
1. **冷启动第一轮只学基线、不下判断**
2. **上报之后把基线上抬**（`if (base < n/2) base = n/2`）

### 顺带：我的工具也骗过我一次

`serial_lab.py` 最初只打印它认识的行（`[win]`/`[surge]`/`[post]`），
**把 `[ble]` 和 `[tick]` 静默丢弃了**。结果我误判"固件没打印 BLE 日志"，白查了一轮。

修法：不认识的行走"原样打印"分支。**工具不能替人做过滤决定，否则排障时会被自己骗。**

## 8. 面试怎么说（90 秒）

> "我的告警研判系统原来只有一个数据源——日志。为了验证管线不是只对日志有效，我加了一层边缘采集：一块 ESP32 每 5 秒采一次无线侧指标，**在本地做窗口判定和去抖，只有异常才上报**，正常时一条不发，所以带宽口径是 180 个采样比 1 条事件。
>
> 真正难的不是采数据，是三个硬件特有的问题：设备**没有可靠时钟**，所以我不信它的时间，用 `boot_id + seq` 保序，服务端按接收时间落时间戳；设备**会断网也会重启**，所以我做了 200 条环形缓冲、幂等重放，重启原因本身当成一条可用性告警；**掉线只能服务端算**，因为设备没法上报'我掉线了'。
>
> 这些我都做了对照实验：拔网 30 秒后 0 丢失，重复投递 accepted=0/duplicated=N，重启能区分是软件复位还是供电不足。"

**结构**：动机（验证管线通用性）→ 做法（边缘降噪）→ 真正的难点（3 个硬件问题）→ 证据（实验数字）。
最后一段才是区分度。

### 五个必被追问的问题

| 问 | 答 |
|---|---|
| 为什么不直接每秒上报，让服务端聚合？ | 带宽和时延都不划算：WiFi 上报一次约 300 字节，1 Hz 一天 26 MB；而且服务端本来就在做聚合，边缘再算一遍是浪费，**更关键的是断网时全丢**——边缘缓冲至少能保住 |
| 设备时间不准，聚合窗口怎么办？ | 窗口在设备侧只算长度（`dev_ms` 差值），服务端一律按接收时间落 `ts`；跨设备排序我承认不准，所以**没做跨设备关联**，这是已知局限 |
| 幂等怎么实现的？ | 键是 `boot_id + seq`。补传时服务端先查表，命中就计入 duplicated 不写库。设备侧只有收到 200 才删缓冲，所以"发出去了没收到响应"可以安全重发 |
| 这个设备和你的 Agent 有什么关系？ | 设备只做**数据生产**，研判还是 Agent 那条链路。它的价值是给管线加了"非日志"的输入，验证了 `agentkit` 那个内核不依赖数据来源 |
| 有传感器就能漏报/误报，你怎么知道准？ | 我没有工业级准确率，也不假装有。我只有两组对照：去抖前 vs 去抖后的上报数（抑制效果），和人工触发 vs 自动触发的召回（能抓到我故意制造的那次突增）。**样本太小，结论是方向性的** |

## 9. 已知局限（主动说，别等被问出来）

1. **没有跨设备时间对齐**：两台设备的 `seq` 不可比，做不了"多设备同一时刻"的关联分析
2. **探测请求计数受环境影响大**：人多人少、手机省电策略都会让基线漂移，指数平均只能缓解
3. **钓鱼热点判据很粗**：只看"同名不同 BSSID + 信道/加密不一致"，对正规企业 Mesh 网络会误报
4. **单设备**：没有设备注册、没有凭证轮换（`INGEST_TOKEN` 是静态共享令牌）
5. **没有任何认证之外的防护**：`/ingest` 没有限流，理论上可被灌数据（本地演示环境可接受）
