# 走过的弯路

> 这份文档的目的只有一个：**证明这些代码是在真实环境里被打过脸的**。
>
> 代码可以生成，文档可以生成，**但"踩了什么坑、当时怎么误判、最后怎么发现"生成不出来**——
> 因为它需要先真的错一次。
>
> 下面每一条都带：**当时的判断 → 事实 → 代价 → 改法**。顺序不能乱，乱了就成了事后总结。

---

## 1. 网段判断：用 IP 前缀猜内外网，漏掉了两类

**当时的判断**：`10.` / `172.16–31.` / `192.168.` 开头就是内网，简单可靠。

**事实**（被真实数据打脸）：
- `127.0.0.1` **不在任何内网段表里** → 被判成外网 → 本机调试的告警全部按"外网攻击"处理
- `172.24.x.x` 是 Docker/NAT 常用段，**前缀判断会把它当内网**，实际那是靶场攻击机所在的段
  → 攻击流量被判成"内网业务行为" → **这一类是漏报，不是误报**

**代价**：第一版研判把 4 条真实攻击判成了业务行为。这个错**在指标上完全看不出来**——
降噪率反而更高（因为"判成误报"比"判成真"更容易自动关闭），看着更漂亮。

**改法**：不猜前缀，改用**网段台账**（`config.ZONE_RULES` 显式列出已知段 + 未知就标 unknown）。

**为什么这条值钱**：它说明了一件事——**"降噪率变好"可能是漏报变多**。
所以后来我坚持误报和漏报分开评估，不敢只报一个数。

## 2. 聚合：一开始想用语义相似度，方向错了

**当时的判断**：告警文本相似就用向量聚类，这样"措辞不同但同一件事"也能合起来。

**事实**：语义相似会把**完全无关的两件事合到一起**：
- 内网员工登录失败 + 境外 IP 爆破登录 → 都是"登录失败"，语义高度相似 → 合成一个事件
- 结果：一个真实攻击被"员工误操作"的上下文稀释，判成误报

**根因**：判断"是不是同一件事"要看**实体（谁、对什么、用哪条规则）**，不是看**文字像不像**。

**改法**：改成实体指纹 `asset | 归一化 src_ip | rule | technique` + 10 分钟时间窗。
语义只用在**检索处置 SOP** 上（那里文字相似确实是有用信号）。

**代价**：语义聚类那一版写了一整天，最后全删了。

## 3. 检索：向量模型最好，但混合反而更差

**当时的判断**：换成 BGE 向量模型，检索质量一定提升；再加一路混合检索，应该更好。

**实测**（同一套难例）：
- bigram → BGE：难例命中 **+19pt**（确实提升明显）
- 但**混合（bigram + BGE）比单用 BGE 更差**，因为两路分数尺度不同，融合时高质量那路被拉低
- 而 BGE 让 P95 多花约 300ms，把延迟预算吃掉了

**结论**：最后选了 bigram + BM25 + RRF（不引入模型）。
**这不是"最好的方案"，是"在 2.5 秒 P95 预算内最不坏的方案"。**

> 这条是我最怕被问到的：如果面试官问"你为什么不用向量模型"，正确答案不是"RRF 更好"，
> 而是"**我试过，它更好但更贵，我的预算买不起**"。

## 4. 阈值：25 是拍的，然后被正常行为打穿

**当时的判断**：探测请求阈值地板设 25，"留点余量，防误报"。

**事实**（量了 38 个窗口之后）：
- 空闲基线：min 3 / 中位 12 / **max 20**
- **单台电脑正常扫 WiFi：单窗口最高 28** → 正常行为就能顶破 25

**代价**：任何人扫一下 WiFi 就可能触发告警。"连续 3 个窗口"只是把误报从"立刻"推迟到"15 秒后"。

**改法**：地板改 40（约 3× 中位），并保留连续 3 窗口 + 5 分钟冷却。

**顺带得到的认知**：单台设备怎么扫都到不了 40 → 这个阈值实际在识别"**多人/多设备持续在场**"，
不是"有人在扫描"。想识别后者得换信号（看 probe 的目标 SSID 前缀），**调阈值没用**。

## 5. 心跳 300 秒、掉线阈值 120 秒 → 设备"永久假离线"

**当时的判断**：心跳 5 分钟一次够了，掉线阈值 2 分钟很灵敏。

**事实**：设备两次心跳之间**必然**超过 120 秒 → 后端每次都判它掉线。
板子明明活着，页面上一片"心跳丢失"。

**根因**：**掉线阈值必须 ≥ 3× 心跳间隔**，否则这个告警在数学上一定误报。

**改法**：心跳 60 秒、阈值 180 秒（丢 3 次才判死）。

> 这个坑纯模拟器永远测不出来——模拟器想发就发，没有"间隔"这回事。
> **只有接上真设备、等两分钟，才会看到这个错。**

---

## 6. BLE 和 WiFi 混杂模式抢射频

**当时的判断**：加个 BLE 扫描通道，WiFi 照常工作，互不影响。

**事实**：串口里**完全没有 `[ble]` 输出**。查了半天以为 BLE 初始化失败。

**根因**：WiFi 混杂模式把射频钉在"收 802.11 管理帧"的状态，BLE 扫描拿不到结果。
两者共用一个射频。

**改法**：扫 BLE 前 `esp_wifi_set_promiscuous(false)`，扫完立刻开回来。
**代价**：那 2 秒的 probe request 会漏数——这个代价写在文档里，没藏。

## 7. 开 BLE 后固件超 flash 上限 134%

**当时的判断**：加个 BLE 库，不会大多少。

**事实**：
```
Sketch uses 1763179 bytes (134%) of program storage space. Maximum is 1310720 bytes.
Error during build: text section exceeds available space in board
```

**改法**：换分区方案 `PartitionScheme=huge_app`（3MB APP）→ 降到 56%。
**代价**：huge_app 没有 OTA 分区，不能空中升级，只能插线烧。这个取舍写进了 README。

## 8. 基线只在"不越界"时更新 → 环境一变就永久误报

**当时的判断**：基线用指数平均，越界时不更新（怕异常值污染基线）。

**事实**：换到一个本来就有 20 台蓝牙设备的地方，默认基线是 6 → 立刻越界 →
**越界时基线不更新 → 永远越界 → 每 5 分钟报一次**。

**改法**两条：① 冷启动第一轮只学基线不判断；② 上报之后把基线**上抬**（`base = n/2`）。

## 9. 排障工具自己把日志吞了

**事实**：BLE 明明在跑，串口工具里却看不到任何 `[ble]` 行。查了一轮固件、重启、换波特率。

**根因**：我写的 `serial_lab.py` 只打印它认识的行（`[win]`/`[surge]`/`[post]`），
**未识别的行被静默丢弃**。`[ble]` 和 `[tick]` 正好属于"不认识"。

**改法**：加"未识别行也原样打印"分支。

> **教训**：排障工具的过滤逻辑不能替人做决定。否则你会在错误的地方找一天。

---

## 10. 改简历时用字符串替换，静默失败

**事实**：把"21 个单测 → 27"、"CI 五关 → 六关"批量替换，脚本返回成功，PDF 导出也成功。
渲染成图一看，**"工程能力"那行还是"21 个用例 / CI 五关"**。

**根因**：那行文案在源码里是两段字符串拼接的，`replace` 匹配不到完整串，**但不报错**。

**改法**：替换加 `assert old in s`；改完**回读 PDF 做关键词计数自查**（`21 个`=0、`27 个`=3）。

> **教训**：凡是"批量替换"，都要有一条独立的验证通道，不能只看返回值。

## 关于"AI 帮了多少"（可选，面试时自己决定怎么说）

这个项目的真实分工，建议你照实说，因为它经得起追问：

- **设计与判断归我**：四层为什么要拆、指纹为什么不用语义、阈值为什么是 40、
  人机边界画在哪、预算怎么反推候选数——这些是我定的，也都踩过错。
- **代码有不少是 AI 辅助写的**：尤其是重复性的脚手架、测试用例、文档初稿。
  我用它来加快"写"这一步，但"做什么、为什么这么做"是我判断的。
- **AI 帮我发现过 bug**：比如 `WiFi.BSSID(i) != WiFi.BSSID(j)` 比的是指针不是内容。
  但它也提过错的建议，我否掉了不少。

**这个说法比"全是我写的"安全得多**：前者经得起追问，后者一被问细节就崩。

## 怎么用这份文档

1. **面试前读一遍**，挑 2 条准备成故事（推荐 #1 和 #5：一个体现判断力，一个体现真机经验）

3. 被问"这是不是 AI 写的"→ 不否认，转成"AI 替我写代码，但坑是我踩的"，
   然后顺手讲 #5（心跳阈值那个数学错误，AI 不会主动想到）
