# 架构与标准企业级 Agent 骨架的对照

> 参照对象：某《AI Agent 面试全攻略》配套的 `project-python`（自称"企业级实战项目"，
> 但其 README 原文写着"**当前仓库为可运行的最小骨架，业务逻辑可在对应模块中逐步实现**"）。
>
> 写这份文档的目的：**知道自己缺什么、为什么缺、要不要补**。
> 被问"你的架构和标准企业骨架差在哪"时，直接照这份答——比说"我做的比较完整"强得多。

## 2. 本次补齐的两块（都是可验证的）

### 2.1 三态熔断器（`app/resilience.py`）

**补之前的问题**（真实存在，不是理论）：
研判层对每个事件调一次模型。模型服务挂掉时，`_call_llm` 每次都要等满超时（默认 25s）。
40 个事件 = 最坏 **1000 秒**，而且这 40 次全是注定失败的调用。

**补之后**：连续失败 3 次开门 → 后续请求**毫秒级直接拒绝** → 冷却 30 秒后放 1 个探针试水。

**实测对比**（`python scripts/breaker_experiment.py`，把模型地址指向黑洞 IP、单次超时压到 2s）：

| | 无熔断（阈值 999） | 有熔断（阈值 3） |
|---|---|---|
| 全量研判耗时 | **80.2s** | **6.1s** |
| 真实模型调用 | 40 次 | **3 次** |
| 被直接拒绝 | 0 | 37 次 |

→ **快 13.1 倍，真实调用从 40 降到 3。** 按默认 25s 超时推算，是 1000s → 约 75s。

**设计取舍（会被追问）**：
- 用**连续失败**而不是错误率：单实例低 QPS，错误率要滑窗，复杂度不划算
- 冷却用**固定时长**而不是指数退避：模型故障多是分钟级，退避会让恢复时间不可预测
- 半开只放 **1 个探针**：放多了会把刚恢复的服务再打死（惊群）

### 2.2 评测门槛进 CI（`scripts/eval_gate.py` + `ci.sh` 第 4 关）

**补之前的问题**：单测只证明"函数没写错"，不证明"整体效果没退化"。
把 `WINDOW_MIN` 从 10 改成 1，**单测全绿**，但降噪率从 98.67% 掉到 **94.70%**、簇数从 40 涨到 **159**。

**门槛判据**（用区间不用单点，单点会被过拟合）：

| 检查 | 门槛 | 当前值 |
|---|---|---|
| 降噪率 | ≥ 0.95 | 0.9867 |
| 簇数 | 30–60 | 40 |
| 平均每簇 | ≥ 50 | 75.0 |
| 路由合法性 | 只允许 auto_close/review/escalate/need_human | 3 种合法 |
| 单簇上限 | ≤ 800 | 500 |

**已验证它会红**：`WINDOW_MIN=1` 时退出码 **1**，正常时 **0**。
**一个从不会失败的门槛，等于没有。**

## 3. 缺但**不补**的（附理由，这是加分项）

### 3.1 不拆 `api/routes/`

骨架按领域拆 chat/document/health。我的接口只有 14 个、都围绕同一套数据，
拆成 3 个文件的结果是每个文件 40 行 + 一堆 import。**在 900 行的项目里，拆是形式主义。**
如果接口涨到 30+ 或要分团队维护，再拆。

### 3.2 不上 Redis / Milvus / PostgreSQL

骨架的架构是"面向多实例、可横向扩容"的。我的场景是**单机单实例、SQLite 单写者**。
上了 Redis 只是多一个要运维的进程，没有解决任何真实问题。
**要扩的时候先换 Postgres、缓存外置，再谈 Milvus** ——这个顺序不能反。

### 3.3 不做 `tools/router.py`

骨架需要路由是因为工具多（几十个）。我只有 5 个工具，且都是按名字精确调用。
**加一层意图识别只会引入"路由错了"的新失败模式**，收益为负。

> 这三条的共同逻辑：**架构复杂度要为真实的约束服务**。
> 面试时说"我不上 Redis 因为单机单写者，上了只是多一个要运维的进程"，比说"我用了 Redis"更能证明你懂工程。

## 4. 缺且**该补**的（已排期）

| 缺口 | 为什么该补 | 成本 | 补完能说什么 |
|---|---|---|---|
| **反思 Reflection** | JD 里"失败恢复"是高级岗分水岭 | 0.5 天 | 40 个事件打回 3 个、改判正确 2 个 |
| **长期记忆** | JD 明确写"记忆槽位/跨会话隔离" | 1 天 | 新事件命中历史结论的复用率 X% |
| **Planning** | JD 三个方向都写了 Agent/Planning | 1 天 | 高危事件计划步骤采纳率 X% |
| **reranker** | JD 写"重排序"，我现在只有 RRF | 0.5 天 | Recall@5 加前/加后对比 |
| MCP（协议层，不在骨架里但 JD 高频） | 外部工具标准化接入 | 1 天 | 在 Cursor 里调用我的接口 |

> 这 5 项做完，上表 §1 的"缺 4 个"会收敛到 1 个（orchestrator，多 Agent 编排，暂不需要）。

## 5. 面试怎么讲这份对照（60 秒）

> "我拿一个'企业级 Agent 骨架'的目录结构当检查清单，逐项对了一遍：14 个核心模块我有 8 个，
> 这次补了 2 个（三态熔断、评测门槛），还有 4 个没做。
>
> 补的两个都带数字：熔断让模型挂掉时的全量研判从 80 秒降到 6 秒，真实调用从 40 次降到 3 次；
> 评测门槛进了 CI，我故意把聚合窗口改成 1 分钟，单测全绿但降噪率掉到 94.7%，门槛立刻把流水线打红。
>
> 没做的四个我分了类：**反思、长期记忆、Planning、reranker 在排期里**，因为 JD 明确要求；
> **orchestrator 多 Agent 编排暂时不做**，因为我只有一个 Agent，硬上等于给自己造复杂度；
> 另外骨架里的 Redis/Milvus 我也没上——我是单机单写者，上了只是多一个要运维的进程。"

**这段话的结构**：对照 → 补了什么（带数字）→ 没补的（带理由和排期）→ 反例（为什么不上 Redis）。
最后一段才是区分度。
